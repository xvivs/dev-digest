## Systemic patterns

1. **Every interactive route is `"use client"` at the page-entry level, with no server data fetching anywhere in the app.** This is the root cause behind NEXT-5 (useSearchParams CSR bailout), NEXT-6 (no per-route metadata), and shapes NEXT-10 (dates render with real per-request server HTML rather than a static shell, so hydration mismatches are live, not moot). One architectural decision, three findings.
2. **API response data is never validated with the zod schemas the project already vendors for exactly this purpose** — `apiFetch` (TS-1), SSE payloads (TS-2), and settings JSON (TS-3) are all blind-cast. The schemas exist (`src/vendor/shared/contracts/*.ts`) and are used server-side; the client half of the "one schema, three jobs" idea from ADR 0001 is unused.
3. **`noUncheckedIndexedAccess` is turned on but routinely bypassed with `!` instead of narrowed** (TS-7, TS-7b) — the strictness setting is present but not yet a house style.
4. **Two parallel type universes for the same UI concepts** — `@devdigest/ui` declares its own `Severity`/`Category` (TS-5) and returns raw `string` from select inputs (TS-6) instead of consuming/re-exporting `@devdigest/shared`'s zod-inferred unions, forcing casts at every app-layer boundary crossing.
5. **No Next.js special-file conventions are used at all** — zero `error.tsx`, `not-found.tsx`, `loading.tsx`, `global-error.tsx` across the entire `app/` tree (NEXT-1–4), and `notFound()`/`redirect()` are never called; the app has instead built its own ad hoc equivalents (`isError` branches, `<RepoNotFound/>`) everywhere.

## ADR candidates

- **Client-fetched SPA-over-Fastify vs. Server Component data fetching.** The current architecture (every route client-rendered, all data via TanStack Query hooks hitting the Fastify API from the browser) is a coherent, deliberate choice for this course starter, but it directly forecloses per-route metadata (NEXT-6), makes every `useSearchParams()` route pay the CSR-bailout cost (NEXT-5), and moves date formatting out of the server's control (NEXT-10). Worth an ADR either affirming "client-only by design, metadata/SEO out of scope for L01" or planning the L0x lesson where select routes move to server fetching.
- **Response validation boundary for `@devdigest/shared` contracts on the client.** TS-1/TS-2/TS-3 are all instances of the same gap: no policy exists for *where* a zod-validated boundary should sit (`apiFetch` itself vs. per-hook vs. per-component). An ADR could pick one (recommend: inside `apiFetch`, parameterized by schema) before the pattern spreads further across ~25 hooks.
- **Single source of truth for `Severity`/`Category`/enum-ish UI types shared between `@devdigest/shared` and `@devdigest/ui`.** TS-5/TS-6 show the design system re-declaring types that already exist as zod-inferred unions one package over. Given ADR 0003 already made `vendor/ui` editable specifically to fix cross-cutting gaps, this is the same category of problem and could ride the same precedent.

## What's good

- `QueryClient` is created via `React.useState(() => new QueryClient(...))` inside `Providers` (`providers.tsx:22-24`) — correctly scoped per component instance, not a module-level singleton that would leak across requests/users in an App Router tree.
- `theme.tsx` reads `document.documentElement` only inside `useEffect` (`theme.tsx:17-20`), the correct pattern to avoid the exact hydration mismatch that `ReviewRunAccordion`/`RunHistory` fall into with `Date` (NEXT-10) — the codebase already knows the right pattern, it's just inconsistently applied.
- `layout.tsx`'s inline `themeNoFlashScript` (`theme.tsx:44`) is a deliberate, narrow `dangerouslySetInnerHTML` for a pre-paint theme script with `suppressHydrationWarning` scoped to exactly the elements browser extensions mutate (`layout.tsx:18,27`, with a comment explaining the one-level-deep scoping) — a well-reasoned, documented hydration-mismatch mitigation rather than a blanket suppression.
- `pulls/[number]/page.tsx:30-42` (`parseSeverity`) deliberately avoids importing the zod `Severity` schema as a *value* from `@devdigest/shared`'s vendored barrel, with a comment explaining the exact webpack `.js`-specifier resolution failure this would trigger (also documented in `client/INSIGHTS.md`) — a correct, self-aware workaround rather than an accidental gap, even though the broader pattern (TS-1) is that the client doesn't validate with zod at all.
- Route params/search params are consistently read through `useParams()`/`useSearchParams()` client hooks rather than mixing in the Next 15 async `params: Promise<...>` Server Component pattern inappropriately — no route in scope misuses the async-params API, because none of them are Server Components that receive it.
