# reviewer-core/specs/

Plans for engine work that is **not built yet** — a new prompt slot, a review
strategy, a change to structured output or grounding.

A spec lands before the code. Because prompt changes move every review's output,
a spec here should say what behaviour is expected to shift and how you will tell.

Once the work ships, either delete the spec or promote the durable parts to
`../docs/`. Features that also change the server belong in `../../specs/`.

Not here: how the engine works today (`../README.md`, `../docs/`) or debugging
findings (`../INSIGHTS.md`).
