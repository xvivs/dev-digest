## Problem & Motivation

To get a useful Overview tab (intent, risks, blast radius) a PR needs three things that are started from three different places today:

- a clone: `POST /repos` / `POST /repos/:id/refresh` enqueue the `clone` job (`server/src/modules/repos/service.ts:98-103,117-122`);
- an index: the clone job enqueues `repo-intel-index` (`repos/service.ts:68`), Refresh enqueues `repo-intel-refresh` (`:129`), Conventions' Resync enqueues `repo-intel-resync` (`repo-intel/routes.ts:53`);
- a brief: `POST /pulls/:id/brief/derive` (`brief/routes.ts:54-64`) or the import-time scheduler.

The Overview has no single "make this ready" action and no signal of how old the index is. Worse, nothing prevents two indexings of the same repo from running at once: `container.jobs` runs 3 jobs concurrently (`platform/jobs.ts:52`), `enqueue` always inserts and schedules (`jobs.ts:65-120`, no dedupe), and `runFullIndex` deletes all symbols and then inserts them outside a transaction (`repo-intel/repository.ts:249-252`), so two overlapping runs can interleave deletes and inserts. A `withTimeout` firing also frees the queue slot while the handler keeps running (`resilience.ts:13-24`, server INSIGHTS 2026-09-30 "Per-job bookkeeping ... must hang off `job.done`"), which opens the same race even at concurrency 1.

## Goals / Non-goals

### Goals

1. One button, **Prepare overview**, in the Overview tab header. It starts only the missing steps: clone, repo-intel index, brief derive (intent + risks).
2. A tooltip on the button shows the time of the last real index run, or "Never indexed".
3. Two indexing pipelines for one repo can never run at the same time in one API process, whatever started them (Prepare, Refresh repo, Resync, clone follow-up).
4. Double click, two tabs, or Refresh repo + Prepare at once start at most one index job, one clone job and one brief job.
5. Readiness is cheap: no LLM call, no blast computation, no GitHub call.

### Non-goals

- Force reindex from the Overview. A `full` index at the clone HEAD is left alone.
- Drift between the clone and `origin` (the clone job on an existing clone only fetches, `adapters/git/simple-git.ts:94-97`; HEAD does not move). Out of scope.
- SSE progress. Polling only.
- Multi-instance safety. The lock is in-process (ADR 0020 single-instance assumption; see Decisions D3).
- Gating the inline facade calls `indexRepo` / `refreshIndex` / `resyncRepo` used by unit tests and the CI path (`repo-intel/service.ts:122-162`). Only the three JobRunner handlers are gated.
- Changing the existing Derive / Refresh buttons in IntentCard and RiskAreas. They stay as point actions.
- Backfilling `last_indexed_at` for existing rows (D6).

### Decisions

**D1 — Module shape (human decision, recorded).** New module `server/src/modules/overview/` at full onion depth: `constants.ts`, `domain.ts` (pure: `classifyIndex`, `classifyBrief`, `planPrepare`), `ports.ts`, `service.ts` (`OverviewService`), `wiring.ts`, `routes.ts`. No `repository.ts`: the module owns no table. Every port is adapted in `wiring.ts` from a container seam: `container.reviewRepo.getPull` (tenancy + `repoId`), `container.repoClone`, `container.repoIntel`, `container.prBrief`, `container.config.repoIntelEnabled` (read through `repoIntel.getIndexReadiness`, below). The module imports no other module (`arch:check` rule `modules-no-cross-import`, `server/.dependency-cruiser.cjs:37-46`).

**D2 — Readiness is computed on the server, and the plan is the server's (human decision).** `planPrepare(readiness)` is the single source of "what Prepare would do now". The GET returns its result as `actions`, so the button state and the POST cannot disagree. The POST recomputes readiness at request time; it never trusts client input (the body is empty).

**D3 — Per-repo index gate in repo-intel (human decision + contention policy, planner; instance placement amended by spec server/07).**

- A generic in-process primitive `KeyedGate<T>` lives in `server/src/platform/keyed-gate.ts` (pure, no I/O, no imports from `modules/**`). Precedent for a module-level keyed in-process lock: `withRepoLock` (`adapters/git/simple-git.ts:30-48`).
- The **instance** is a private field of the container's single `RepoIntelService` (`indexGate`, `repo-intel/service.ts:161-168`; spec server/07). It was first a module-scope `WeakMap` keyed by container, because the service existed twice per app; spec server/07 removed the second instance, so handlers and facade now share the field. Separate test apps get separate containers and so separate gates, and a trailing pass never runs on another app's db/git. Production builds one container (`server.ts:8`). Tests still use a unique `repoId` per case (PC-5).
- State per `repoId`: `queued` (reservations whose job has not settled), `running` (a handler body is executing), `trailing` (a coalesced follow-up of type `IndexTrailing = { full: boolean; sync: boolean; workspaceId?: string }`, or `null`).
- `isBusy(repoId)` = `queued > 0 || running`.
- **Reserve at request time.** `repoIntel.requestIndex(ws, repoId, kind)` checks and reserves synchronously, before its first `await`, so two callers in one tick cannot both pass (single-threaded event loop). Idle: `queued += 1`, enqueue the job of that kind, release the reservation exactly once when `job.done` settles or when `enqueue` throws (server INSIGHTS 2026-09-30, `job.done` settles exactly once). Busy: no enqueue; merge `trailingFor(kind, workspaceId)` into `trailing`; return `{ queued: false, reason: 'in_flight' }`.
- **Lock at handler time.** All three handlers (`INDEX`, `REFRESH`, `RESYNC`, today `repo-intel/service.ts:172-181`) run their body through `gate.runExclusive(repoId, contendedAs, body, runTrailing)`. If another body for the same repo is running, the handler does not run its body: it merges `contendedAs` into `trailing` and returns (the job is `done`). The lock is released when the handler body **and** its trailing passes finish, not when JobRunner's `done` settles (on timeout `done` settles early while the handler keeps going).
- **Trailing pass (code-review F3/F5/F6).** Merge is a field-wise OR (`mergeTrailing`, `repo-intel/service.ts:116-119`): a coalesced full index or resync is never downgraded to a plain refresh. The gate does not run the pass inside the finishing handler. When the key goes idle with `trailing` set, `settle` takes it, takes a fresh reservation via `hold` (so the key never reads idle during the hand-off) and passes both to the `dispatch` callback (`platform/keyed-gate.ts:119-140`). `dispatchTrailing(container, repoId, t, release)` (`repo-intel/service.ts:126-151`) enqueues it as its own job on `container.jobs` (`resync` if `sync`, else `index` if `full`, else `refresh`), and releases the reservation when that job's `done` settles or when the enqueue fails. A pass without `workspaceId` is dropped with a `warn`. A body error is rethrown so JobRunner records it; a dispatch failure is logged at `warn` and released. There is no window in which the key reads idle while a pass is pending. Why trailing instead of dropping: a request that arrives while a run is in progress may carry newer clone state (the clone job's follow-up index); dropping it would leave the index behind. `refreshIndex` on an unchanged HEAD is a cheap `sha_unchanged` touch (`pipeline/incremental.ts:97-106`).
- **Idle cleanup.** When `queued === 0 && !running` and no `trailing` is pending, the key is deleted. A pending `trailing` with no dispatcher configured is dropped with a `warn`.
- **Single-instance.** The gate relies on ADR 0020's one-API-process-per-database assumption. A second process (a script, a replica) gets its own gate. Flagged for ADR 0025.

**D4 — All index enqueues go through the gate.** `refresh` only enqueues the clone; the clone follow-up requests the index (one per click, F1; `repos/service.ts:160-168`). The clone follow-up calls `container.repoIntel.requestIndex(...)` instead of `container.jobs.enqueue(INDEX_JOB_KIND|REFRESH_JOB_KIND, ...)`; the resync route (`repo-intel/routes.ts:53`) calls its local service's `requestIndex(..., 'resync')`. This removes the import of `../repo-intel/constants.js` from `repos/service.ts:11-14`, a baselined cross-module violation (`.dependency-cruiser-known-violations.json:114-126`, PC-8/AR-6), and closes the window where an index job is queued but invisible to readiness. The follow-up kind depends on what the clone job did (PC-9): the handler reads `clone_path` **before** cloning, through a new `RepoRepository.getCloneBasics(repoId) → { workspaceId, clonePath } | undefined` (one query, replaces the later `workspaceIdFor` call, which is deleted, PC-15; `repos/repository.ts:70`); it requests `'index'` only when that was `null` (a fresh clone), and `'refresh'` otherwise (an existing clone only fetches, `simple-git.ts:94-97`, and an incremental on an unchanged HEAD is a cheap touch). This makes AC-9 deterministic and ends today's full wipe-and-rebuild on every Refresh repo click (`repos/service.ts:68,117`). Planner refinement of "the clone job already enqueues the index" (listed under Needs approval). The clone follow-up keeps its `try/catch` (a `ContainerOverrides.repoIntel` mock may lack the method). The rule is written down where agents read it (AR-6): #10 rewrites the `service.ts:108-113` comment, #11 rewrites the `routes.ts:1-12` header, and #29 adds a Rules bullet to `server/src/modules/repo-intel/AGENTS.md`. After step 5 the stale baseline entry is pruned with `pnpm arch:baseline`; the baseline diff must contain deletions only (`server/AGENTS.md`: regenerate only after removing old ones).

**D5 — Clone facade `container.repoClone` (human decision: a new port).** `RepoCloneFacade` is declared in a new `server/src/modules/repos/types.ts` and type-imported by the container, the same pattern as `PrBriefFacade` (`modules/brief/types.ts:1-5`, `container.ts:36-37,178-182`). Methods:

  - `getCloneStatus(workspaceId: string, repoId: string): Promise<{ cloned: boolean; inFlight: boolean; lastFailure: CloneFailure \| null } \| undefined>` with `CloneFailure = { reason: CloneFailureReason; at: Date }` (`repos/types.ts:9-20`, AR-1)
  - `requestClone(workspaceId: string, repoId: string): Promise<{ queued: boolean; reason?: 'in_flight' | 'no_handler' } | undefined>`

  `undefined` = repo not in the workspace. Built by a new `repos/wiring.ts` `buildRepoService(container)` that injects `new RepoRepository(container.db)` (AR-4): the `RepoService` constructor becomes `(container, repo: RepoRepository)` with a type-only import of the repository, and `repos/routes.ts:21` gets its service from `wiring.ts`. This removes the baselined `service.ts → repository.ts` edge (`.dependency-cruiser-known-violations.json:71-83`) and gives the gate logic a constructor seam for fakes. The field stays named `repo`, so `test/repos-clone-failure.test.ts:58-62` keeps working (it constructs `new RepoService(container)`; that call gains the second argument). The container holds one `RepoService` (`container.repoService`) that both the routes and the `repoClone` facade use (spec server/07). A `KeyedGate<never>` private field (`cloneGate`) of the container's single `RepoService` (spec server/07) gates `add`, `refresh` and `requestClone` (reserve) and the `clone` handler (`runExclusive`; a contended clone handler returns without cloning). A clone is never coalesced into a trailing pass. `cloned` = `repos.clone_path IS NOT NULL` (`db/schema/repos.ts:16`). The clone handler requests the follow-up index **before** it releases the clone gate, so readiness never sees "clone done, nothing in flight" in between.

  **Clone failure record (AR-1, human-approved 2026-10-01).** A failed clone used to vanish from readiness: `no_clone`, not in flight, the same plan, no reason. `runCloneJob` now writes the last failure to an in-memory record in `repos/service.ts`: the private field `cloneFailures: Map<repoId, CloneFailure>` of the container's single `RepoService` (spec server/07; ADR 0020 single instance; gone after a restart, so readiness merely stops explaining a past failure). The entry is cleared at the start of each attempt (`:88`), so success leaves none, and set in the `catch` around `git.clone` (`:101`) before the error is rethrown. Only the enum leaves the module: `classifyCloneFailure(err) → 'not_found' | 'auth' | 'network' | 'unknown'` in `repos/helpers.ts:53-56` (pattern table `CLONE_FAILURE_PATTERNS`); the raw message may carry the clone URL or the token and is never stored. `getCloneStatus` returns the entry as `lastFailure` (`service.ts:200`). It does not change the plan: `clone` stays offered and the button stays enabled, so a retry is one click and nothing retries by itself.

**D6 — `last_indexed_at` (human decision + write sites, planner).** New nullable column `repo_index_state.last_indexed_at timestamptz`, no default, generated with `pnpm db:generate` (`postgresql-table-design`: timestamptz). It is written only when a run actually re-reads the clone at a HEAD:

  | Write site | Writes `last_indexed_at`? |
  |---|---|
  | `full.ts:269` clean / partial full run | yes |
  | `full.ts:101-105` `no_files` (walk completed, 0 parseable files) | yes |
  | `incremental.ts:263` slice reparse | yes |
  | `incremental.ts:123` `advanceSha` (`no_supported_changes`) | yes (Assumed: the index is now current at the new HEAD) |
  | `incremental.ts:98` `touchIndexState` (`sha_unchanged`) | **no** |
  | `full.ts:88-91` `safePersist` `no_clone` | **no** |

  `IndexStateUpsert` (`repo-intel/repository.ts:47-55`) gains `lastIndexedAt?: Date`. `upsertIndexState` sets it in `values` and in `onConflictDoUpdate.set` only when provided, so a write that omits it keeps the previous value. `advanceSha` sets it. `IndexState` (`repo-intel/types.ts:42-50`) gains `lastIndexedAt: Date | null`; the synthesised no-row state (`service.ts:192-204`) returns `null`. No backfill: `updated_at` is bumped by `sha_unchanged` touches (`repository.ts:327-334`), so copying it would claim runs that never happened. Rows indexed before the migration show "Index time not recorded" until their next real run.

**D7 — Prepare plan (human map, extended by the planner where the map was silent).** `classifyIndex` → `OverviewIndexStatus`, then `planPrepare`:

  | Facts (first match wins) | `index.status` | Prepare action |
  |---|---|---|
  | `repoIntelEnabled === false` | `flag_off` | none (no clone either; Assumed: the clone only feeds the index) |
  | repo not cloned | `no_clone` | `clone` unless clone in flight (the clone job requests the index itself) |
  | cloned but `git rev-parse HEAD` fails | `no_head` | `clone` (PC-6: the clone job fetches, or re-clones when `.git` is gone, `simple-git.ts:94-106`; an incremental would only return `git_head_failed` and write nothing) |
  | no `repo_index_state` row | `missing` | `index_full` |
  | `indexer_version !== INDEXER_VERSION` | `outdated` | `index_full` |
  | status `degraded` or `failed` | `degraded` | `index_full` |
  | status `partial`, same sha as clone HEAD | `partial` | none automatically; offered as the explicit action `reindex_partial` (human decision on OQ-0, D7a) |
  | status `partial`, other sha | `partial` | `index_full` (Assumed: incremental keeps `partial` forever, `incremental.ts` status rule) |
  | status `full`, `last_indexed_sha === clone HEAD` | `full` | none |
  | status `full`, sha differs | `stale` | `index_incremental` (Assumed: the map did not cover it) |

  No index action while `index.in_flight` or `clone.in_flight`. `index_full` → `requestIndex(..., 'index')` (`runFullIndex`); `index_incremental` → `requestIndex(..., 'refresh')`.

  The clone fact comes only from `repoClone.getCloneStatus` (AR-2); `IndexReadiness` has no public `cloned` flag. The same call supplies `clone.last_failure` (D5, D15); `OverviewService` maps `lastFailure.at` to an ISO string (`overview/service.ts:112-113`).

  Brief, per phase, from the brief facade's own view (AR-3): `classifyBrief({ record, stale })` = `record === null ? 'missing' : stale ? 'stale' : 'fresh'`. The overview never compares shas itself, so it cannot disagree with IntentCard / RiskAreas. `intent_failure` / `risks_failure` are the facade views' `lastFailure` per phase (`PrIntentView` / `PrRisksView`, `brief/types.ts:21-33`; both keyed by the current head, `brief/service.ts:157,169`), kept separate so the UI can tell which phase failed (PC-10). `blocked_by` per D7b. `derive_brief` is planned when `!brief.in_flight && blocked_by === null && !cloneWillRun && (intent !== 'fresh' || risks !== 'fresh' || intent_failure !== null || risks_failure !== null)`, where `cloneWillRun` = the plan contains `clone` or `clone.in_flight` (PC-2; a planner extension of the human rule, listed under Needs approval). Intent reads linked docs from the clone (`brief/service.ts:704-716`), so a derive racing the clone stores a `fresh` intent without its docs, which Prepare would never redo. After polling sees the clone finish, readiness offers `derive_brief` and the client continues on its own (D13a), so the user still clicks once. With repo-intel off no clone is planned, so the brief is not held back.

  **D7a — `reindex_partial` (human decision on OQ-0).** `runFullIndex` ends `partial` deterministically at a fixed HEAD (soft budget, graph failure, any parse error, `no_files`; `full.ts:101-105,250-253`), so re-running it automatically would never converge. A pure `planExplicit(facts) → ExplicitAction[]` returns `['reindex_partial']` iff `index.status === 'partial'`, the row's sha equals the clone HEAD, and neither the index nor the clone is in flight. It is never part of `actions`, so "all ready" (`actions: []`, AC-3, AC-17) ignores it. `POST /prepare` runs it only when the body says `{ reindex_partial: true }` **and** the recomputed readiness still offers it; it then calls `requestIndex(..., 'index')` (full index, through the gate). The offer stays after a re-run that ends `partial` again; the tooltip says so. The partial reason comes from the row's stats (D16 `partialReason`).

  **D7b — `provider_not_configured` blocks derive (human decision on OQ-2).** `blocked_by` becomes `'head_moved' | 'provider_not_configured' | null`: `head_moved` wins when either phase failed with it, else `provider_not_configured` when either phase failed with that. A blocked brief plans no `derive_brief`. The UI shows a Settings link (`/settings/api-keys`, the key `SECTION_API_KEYS` in `app/settings/[section]/_components/SettingsView/constants.ts:5`, duplicated as a constant in `PrepareOverview/constants.ts` because routes do not import each other's internals) for `provider_not_configured`. For `head_moved` the cards' own Refresh PR stays the only recovery (D11).

  `planPrepare` takes a facts type `PrepareFacts` (readiness without `actions` and top-level `in_flight`), not the contract type that contains its own output.

**D8 — Brief dedupe without a new trigger.** `PrBriefFacade.requestDerive` (`brief/types.ts:66-70`) gains an optional 4th parameter `opts?: { onlyIfIdle?: boolean }`. With `onlyIfIdle`, after `getPull` resolves and **before** `enqueue` (whose first statement `bump(prId, +1)` is synchronous, `service.ts:335-336`), it returns `{ queued: false }` when `isInFlight(prId)`. No `await` sits between the check and the bump, so two concurrent Prepare calls queue one job. The trigger stays `on_demand` (bypasses the automatic gate, ADR 0022 §5; `runDerive` redoes nothing written after `enqueuedAt`, `service.ts:414-419`). Rejected: a new `'prepare'` trigger, because `runDerive` treats every non-`on_demand` trigger as automatic (attempt cap, `service.ts:425-438`) and `gatherInputs` refuses the persisted fallback for it (`:571-573`).

**D9 — Route limits.** `GET /overview/readiness`: own bucket `config: { rateLimit: { max: 120, timeWindow: '1 minute' } }`. A route-level `rateLimit` object gets its own store, not counted against the global 120/min, keyed per IP (researcher, `@fastify/rate-limit` 11.0.0 `index.js:142-158`, `store/LocalStore.js:46-48`, default `keyGenerator` `index.js:29`), so 2 s polling from up to 4 tabs never eats the global budget. `POST /overview/prepare`: `{ max: 5, timeWindow: '1 minute' }`, the same shape as `brief/derive` (`brief/routes.ts:56`), because one call can cost two LLM requests.

**D10 — Prepare is best-effort per action.** The body is `PrepareOverviewRequest = { reindex_partial?: boolean }` (strict zod object; any other key → 422). The route declares `body: PrepareOverviewRequest.nullish()` and treats a missing body as `{}` (PC-18; DEV-1: Fastify 5 hands the validator `null`, not `undefined`, for an empty payload, `server/node_modules/fastify/lib/validation.js:123`, so `.optional()` would still answer 422; `overview/routes.ts:40-41`). The planned `actions` always run; `reindex_partial` is added to them when the body asks for it and readiness offers it (PC-19). Nothing else from the client reaches the plan. Each planned action is requested independently (`Promise.allSettled`). A request that rejects or returns `reason: 'no_handler'` is listed in `failed`; `reason: 'in_flight'` is neither started nor failed. The POST answers 202 with `status: 'started'` when `started` is non-empty, else `'skipped'`, plus the readiness recomputed after the requests (so it already shows `in_flight: true`). No LLM, GitHub or git work runs inside the request (ADR 0022 "No LLM or GitHub-detail call happens inside a request"). The only git call in either route is `git rev-parse HEAD` for the readiness HEAD comparison (`adapters/git/simple-git.ts:137-139`), the same read `BlastKeySource` already does per GET (spec 04 `:550`).

**D11 — Client placement.** A new `PrepareOverview` component in `client/src/app/repos/[repoId]/pulls/[number]/_components/OverviewTab/_components/PrepareOverview/`, rendered first inside `OverviewTab`'s root (`OverviewTab.tsx:16-18`), above `BriefSection`, aligned right. This is the "header" of the Overview tab; the tab has no other header. **No CTA in `BlastRadiusCard`**: its empty state already explains `no_index` / `index_partial` (`messages/en/blast.json` `reason.*`), and a second index trigger would duplicate the one entry point the human asked for. The existing Derive buttons stay (non-goal). **Refresh PR ownership (human decision on OQ-5, architecture-reviewer's option (a)).** Each phase card owns its own recovery action; `PrepareOverview` renders no Refresh PR. `RiskAreas` changes to match `IntentCard` (`IntentCard.tsx:45-53,104`): when a risks record exists and `last_failure?.reason === 'head_moved' && !inFlight`, it renders the same `BriefFailureNotice` (`BriefFailureNotice.tsx:31` → `BriefFailureAction.tsx:27-34`) above the record. Today it drops the failure in that branch (`RiskAreas.tsx:44-73`). Other failure reasons next to a record stay hidden in RiskAreas, as today. Consequence: an intent-phase `head_moved` also records `head_moved` for risks (`brief/service.ts:462-465`), so both cards show their own Refresh PR; at most one per card. The `RefreshPullButton` extraction and `showRefreshPull` from round 2 are dropped.

**D13 — Polling and invalidation (human decision).** `usePrOverviewReadiness(prId)`: key `["pr-overview-readiness", prId]`, `refetchInterval: data?.in_flight ? 2000 : false`. **D13a — One-click auto-continuation (human decision on PC-2).** The server keeps holding `derive_brief` back while a clone is planned or in flight (D7). The client finishes the job without a second click:

- **Intent.** A user click on the button creates a continuation intent `{ prId, fired: Set<PrepareAction> }` held in a `useRef` inside `PrepareOverview` (in memory, scoped to that PR). It is cleared when the component unmounts or `prId` changes (navigation), when the mutation errors, when a response has non-empty `failed`, and when readiness shows `actions: []` with nothing in flight (done). A click on "Update index" creates no intent.
- **Trigger.** Not a `useEffect` (react-best-practices: no mutation from an effect). `usePrOverviewReadiness(prId, { onReadiness })` calls the latest `onReadiness(prev, next)` from inside `queryFn` after each fetch (the same place it already detects the in-flight → idle transition, D13); the callback lives in a ref so the query key does not change.
- **Decision.** Pure `nextContinuation(intent, readiness) → { call: false } | { call: true; action: PrepareAction }` in `PrepareOverview/helpers.ts`. It returns `call: true` only when an intent exists and `readiness.actions` contains an action from `AUTO_CONTINUE_ACTIONS = ['derive_brief', 'index_full', 'index_incremental']` (constants.ts) that is not in `intent.fired`. `clone` is never auto-continued, and `reindex_partial` cannot be: it is not in `actions`, and the auto POST always sends `{}`.
- **`fired` bookkeeping (PC-17).** On the click, `fired` is seeded with every `AUTO_CONTINUE_ACTIONS` member in the click's `readiness.actions` (what the user's POST already ran). Before each auto POST, every `AUTO_CONTINUE_ACTIONS` member in the triggering `readiness.actions` joins `fired`, not only the one `nextContinuation` picked, because the server runs the whole plan for `{}` (D10).
- **Refs and reset (PC-21).** The `onReadiness` ref is assigned in a `useLayoutEffect`, never during render; that effect's cleanup clears the intent on unmount. `OverviewTab` renders `<PrepareOverview key={prId} prId={prId} />`, so a PR change remounts it with a fresh intent. Firing a mutation from a `queryFn` callback is a deliberate exception to react-best-practices "mutations are triggered from event handlers": the trigger is the poll result (an external event), not a render; recorded in ADR 0025.
- **No-loop guarantees.** (1) Each action is requested at most once per intent, whether the click or an auto POST ran it, so a derive that fails and is re-offered is not retried automatically. (2) The auto POST never carries `reindex_partial`, and an intent ends on the first error or `failed`. Each user click allows at most `AUTO_CONTINUE_ACTIONS.length` auto calls, all under the 5/min prepare limit (D9).

## Acceptance criteria (EARS)

- **AC-1** When `GET /pulls/:id/overview/readiness` is called for a PR in the caller's workspace, the API shall return 200 with a body that parses as `PrOverviewReadiness`, and shall make no LLM call, no GitHub call and no `getBlastRadius` call.
- **AC-2** When either overview route is called for a PR id outside the caller's workspace, the API shall return 404.
- **AC-3** When `POST /pulls/:id/overview/prepare` is called and readiness has `actions: []`, the API shall return 202 with `status: 'skipped'`, `started: []`, and shall enqueue no job on `jobs` or `briefJobs`.
- **AC-4** When Prepare is called for a PR whose repo has no clone and repo-intel is enabled, the system shall enqueue exactly one `clone` job and no index job from the request; the clone job shall request the index when it completes.
- **AC-5** When Prepare is called and the index status is `missing`, `partial`, `degraded` or `outdated`, the system shall enqueue one `repo-intel-index` job (full index).
- **AC-6** When Prepare is called and the index status is `stale`, the system shall enqueue one `repo-intel-refresh` job; when it is `full`, the system shall enqueue no index job.
- **AC-7** While repo-intel is disabled (`REPO_INTEL_ENABLED=false`), readiness shall report `index.status = 'flag_off'`, `actions` shall contain neither `clone` nor an index action, and the tooltip shall show the flag-off text.
- **AC-8** When two Prepare requests for the same PR arrive concurrently (double click, two tabs), the system shall enqueue at most one clone job, at most one index job and at most one brief job in total.
- **AC-9** When Refresh repo (`POST /repos/:id/refresh`) and Prepare are triggered at the same time for one repo, no two index pipeline bodies for that repo shall run concurrently, and at most one full index (`runFullIndex`) shall run for that pair of requests.
- **AC-10** While an index handler body for a repo is running, a second index/refresh/resync handler for the same repo shall not run its body; it shall record a trailing pass and return, and the trailing pass shall run after the first body finishes.
- **AC-11** If a JobRunner timeout settles an index job's `done` while its handler is still running, then the gate shall keep the repo busy until the handler returns.
- **AC-12** When the brief's last failure for the current head has reason `head_moved`, readiness shall report `blocked_by: 'head_moved'`, `actions` shall not contain `derive_brief`, Prepare shall not enqueue a brief job, `PrepareOverview` shall render no Refresh PR button, each of IntentCard and RiskAreas whose phase failed with `head_moved` shall render exactly one (RiskAreas also next to an existing record), and after one is clicked readiness shall be fetched again.
- **AC-12a** When either phase's last failure has reason `provider_not_configured` (and none has `head_moved`), readiness shall report `blocked_by: 'provider_not_configured'`, `actions` shall not contain `derive_brief`, and `PrepareOverview` shall show a link to `/settings/api-keys`.
- **AC-13** When intent or risks are missing or stale, or a phase's last failure has a reason that does not block (D7b), and no derivation is in flight, and no clone is planned or in flight, Prepare shall enqueue one brief job with trigger `on_demand`; while a derivation or a clone is in flight, or when the plan contains `clone`, it shall enqueue none.
- **AC-14** When a full or incremental index run writes `repo_index_state` at a HEAD (rows `yes` in D6), the row's `last_indexed_at` shall be set to the write time; when the incremental pass ends `sha_unchanged`, or the full pass ends `no_clone`, `last_indexed_at` shall keep its previous value.
- **AC-15** When the Overview tab renders, the Prepare button tooltip (title and accessible description) shall show "Last indexed {relative time} · {sha7}" if `last_indexed_at` is set, "Never indexed" if there is no index row or its sha is empty, and "time unknown" for a row with a sha and no time (no backfill).
- **AC-16** While readiness has `in_flight: true`, the client shall refetch readiness every 2 s and show the button busy and disabled; when readiness turns from in flight to idle, the client shall invalidate `pr-intent`, `pr-risks`, `pr-blast`, `repo-intel-state` and `repos` once, and stop polling.
- **AC-17** When readiness has `actions: []`, `explicit_actions: []`, `blocked_by: null` and nothing is in flight, the button shall be disabled with the ready label; with `blocked_by` set it shall be disabled with the blocked label.
- **AC-21** When the index is `partial` at the clone HEAD and nothing is in flight, readiness shall list `reindex_partial` in `explicit_actions` and not in `actions`, `POST /prepare` without `{ reindex_partial: true }` shall enqueue no index job for it, and the button shall read "Update index" when `actions` is empty.
- **AC-22** When `POST /prepare` is called with `{ reindex_partial: true }` and readiness offers `reindex_partial`, the system shall enqueue one `repo-intel-index` job through the gate; when readiness does not offer it, the flag shall be ignored. Any other body key shall get 422.
- **AC-23** While the index is `partial` at the clone HEAD, the tooltip shall name the partial reason (or "unknown"), show `last_indexed_at` (or "unknown"), and state that updating may end incomplete again; after a re-run that ends `partial` again, `reindex_partial` shall still be offered.
- **AC-24** When the user clicks Prepare on a PR whose plan holds `derive_brief` back behind a clone, and a later readiness poll offers `derive_brief`, the client shall send exactly one more `POST /prepare` with an empty body, without another click.
- **AC-25** The client shall send at most one automatic `POST /prepare` per action per click, shall never send `reindex_partial` automatically, shall never auto-continue `clone`, and shall send none after the component unmounts, after a mutation error, or after a response with non-empty `failed`.
- **AC-26** (AR-1) When the last clone job for a repo failed, readiness shall report `clone.last_failure = { reason, at }` with `reason` one of `not_found | auth | network | unknown` and no raw error text; `actions` shall still contain `clone`, the button shall stay enabled, and `PrepareOverview` shall show the matching `prepare.cloneFailed.*` message. When a new clone attempt starts, `last_failure` shall be cleared; nothing shall retry a failed clone automatically, and after an API restart `last_failure` is `null`.
- **AC-18** The migration adding `last_indexed_at` shall be produced by `pnpm db:generate`; no file under `server/src/db/migrations/**` shall be hand-written.
- **AC-20** When `POST /repos/:id/resync` is called for a repo outside the caller's workspace, the API shall return 404 (PC-8; today it enqueues, `repo-intel/routes.ts:47-58`).
- **AC-19** `cd server && pnpm arch:check` shall report no new violation, and `server/src/modules/repos/service.ts` shall no longer import `modules/repo-intel/**`.

## Edge cases

- **Clone in flight, index row stale from a previous clone:** no index action until the clone ends; the clone's follow-up full index takes over.
- **Queued REFRESH + a partial row at another sha:** Prepare sees `index.in_flight` and plans nothing for the index; the REFRESH runs incremental and the row stays `partial`; afterwards readiness offers `index_full` (other sha) or `reindex_partial` (same sha). Accepted (D3 keeps Prepare out of the trailing path to honour "double click → one indexing").
- **Index run longer than 120 s plus a trailing pass:** the job row may end `failed: Operation timed out` while the work finishes; the gate stays busy until it does (AC-11). `jobs` is read by nobody (`app.ts:94-96` reaps runs only).
- **`git rev-parse` fails on a recorded clone:** `no_head` → `clone` (fetch, or re-clone when `.git` is gone). If the fetch cannot repair it, each click repeats a cheap fetch; nothing loops by itself.
- **First Prepare on an uncloned repo with no brief:** only `clone` runs. When polling sees it finish, readiness offers `derive_brief` and the client sends one more POST by itself (D13a). If the tab is closed in between, the brief waits for the next click or the import scheduler.
- **Partial index that stays partial:** "Update index" stays offered after each run; the tooltip names the reason and warns that it may stay incomplete (AC-23). Each click is an explicit full re-run, rate-limited to 5/min.
- **`provider_not_configured`:** blocks `derive_brief` (D7b); PrepareOverview links to Settings → API Keys. After a key is added, the per-block Derive button retries; the failure clears on success (`brief/service.ts:383-387`).
- **PR closed:** `on_demand` derive still runs (`requestDerive` ignores status for `on_demand`, `brief/service.ts:206`). Unchanged behaviour.
- **API restart mid-run:** gates and p-queue are in memory and empty after boot; readiness reports idle; the next click re-plans.
- **Seeded / missing GitHub repo:** the clone job fails (`repos-clone-failure.test.ts`); the gate is released on handler end; readiness shows `no_clone`, not in flight, plus `clone.last_failure` (`not_found`, `auth`, `network` or `unknown`) and the matching message (AC-26). The button stays enabled and each click is one more attempt (the failure is cleared when it starts); nothing retries on its own.
- **Failure record lost:** after an API restart `last_failure` is `null` and the UI shows no message until the next failed attempt (in-memory, ADR 0020).
- **Empty POST body:** Fastify 5 passes `null` to the validator, so the route uses `.nullish()` and treats it as `{}` (DEV-1).
- **Two tabs polling:** each polls readiness at 2 s plus intent/risks at 2 s while in flight; readiness has its own bucket (D9), intent/risks share the global 120/min (pre-existing).
- **Repo deleted while a job is queued:** `runFullIndex` returns `repo_not_found` (`full.ts:80-83`); gate released normally.

## ADR 0025 — Overview prepare: server-planned orchestration, per-repo in-process index lock, last_indexed_at (draft for the doc-writer)

**Context.** The Overview needs clone, index and brief before it is useful, and three screens start them independently. Nothing dedupes jobs: `JobRunner.enqueue` always inserts and schedules, `jobs` runs three at a time, and a timeout frees a slot while its handler keeps running. Two full indexes of one repo can interleave their non-atomic delete-and-insert. The UI also cannot tell how old an index is: `updated_at` moves on every no-op touch.

**Decision.**
1. A server module `overview` computes readiness from the container's facades and a pure `planPrepare` decides the missing steps; `POST /prepare` runs exactly that plan.
2. Index jobs for a repo pass through one in-process `KeyedGate` held as a field of the container's single `RepoIntelService` (spec server/07; separate test apps get separate containers): a synchronous reservation at request time (dedupes enqueues) and a lock around every index handler body (prevents overlap, released when the body ends, not when JobRunner's `done` settles). Requests during a run coalesce (OR-merged) into one trailing pass that the gate dispatches as its own job. Clones get their own gate in the repos module. Instance state is safe because the container holds exactly one `RepoIntelService` and one `RepoService` (spec server/07); the first version used a container-keyed module-scope `WeakMap` while routes built their own second instances.
3. `repo_index_state.last_indexed_at` is written only by runs that read the clone at a HEAD; it is never backfilled.

**Consequences.** Enables one-click preparation, dedupe across every index trigger, and an honest "last indexed" time. Costs: in-memory state (lost on restart, single API instance only, ADR 0020); a trailing pass runs as its own job with its own timeout; pre-migration rows show "time not recorded". Changes Refresh repo: it only enqueues a clone, and the clone job on an existing clone then requests an incremental refresh instead of a full reindex, so a Refresh repo click no longer wipes and rebuilds the index each time (it did, `repos/service.ts:68,117`); a fresh clone still gets a full index. The client fires an automatic `POST /prepare` from a polled query's callback, a deliberate exception to "mutations from event handlers", bounded by D13a. A `partial` index at the clone HEAD is no longer re-run automatically; the user re-runs it explicitly ("Update index"). Forbids enqueuing index jobs except through `repoIntel.requestIndex`, and writing `last_indexed_at` from a touch.

**Alternatives considered.**

| Option | For | Against |
|---|---|---|
| Client assembles readiness from `/intent`, `/risks`, `/index-state`, `/repos` and fires the three existing actions | No new module | Plan logic duplicated in the client; racy (no server-side dedupe); several round-trips per poll; head_moved/flag rules leak into UI |
| Prepare inside the `brief` module | One fewer module | brief would orchestrate clone and index, coupling an LLM module to the indexer; violates "modules never import each other" pressure; brief already 839 lines |
| Partial unique index on `jobs (kind, payload->>'repoId') WHERE status IN ('queued','running')` | Survives multiple processes | `jobs` rows are not reaped on boot (`app.ts:94-96`) and a timed-out handler's row is `failed` while it still runs, so the index both blocks forever after a crash and misses the timeout overlap; needs a migration and 23505 handling in `JobRunner` |
| Postgres advisory lock (`pg_try_advisory_lock(hashtext(repoId))`) around the handler | Cross-process | Session-scoped: needs a dedicated connection held for up to 120 s from the pool; does not dedupe at enqueue time; no "busy" signal for readiness without another query |
| **In-process `KeyedGate`, one per service instance (chosen)** | Zero schema; covers the timeout overlap; gives readiness a free `isBusy`; precedent `withRepoLock` | Single process only; state lost on restart |
