## What Doesn't Work

- **Symlinking `node_modules` into a throwaway git worktree fails in three ways; clone it copy-on-write instead (`cp -Rc` on APFS).** (1) `.gitignore`'s `node_modules/` matches directories only, so the symlink is an untracked file and `git add -A` commits it. (2) dependency-cruiser resolves the link to the real checkout's path, so every `.dependency-cruiser-known-violations.json` entry stops matching and `pnpm arch:check` reports 4 false `presentation-no-db` errors. (3) any package-manager auto-install run inside the worktree mutates the real `node_modules`. Clones of all three packages (~930 MB logical) are near-instant and cost almost no disk (`.claude/skills/pr-self-review/evals/_worktree.sh:14`). _(2026-09-28)_

## Codebase Patterns

- **A cost figure is stored as a pair — value plus `cost_source` ('provider' | 'estimated') — never as a bare number.** Only OpenRouter reports an actual charge (`reviewer-core/src/llm/openrouter.ts`); OpenAI and Anthropic never do, so their figures are always local estimates off `pricing.ts`. One column for both would make `SUM(cost_usd)` silently add invoices to arithmetic. Decision and its constraints: `docs/adr/0002-cost-provenance.md`. _(2026-09-19)_
- **INSIGHTS.md files use a fixed 7-section taxonomy (What Works / What Doesn't Work / Codebase Patterns / Tool & Library Notes / Recurring Errors & Fixes / Session Notes / Open Questions), not the older flat Symptom/Cause/Fix/Recurrence format.** — Migrated by the `engineering-insights` skill (`~/.claude/skills/engineering-insights/SKILL.md`) to match the course lesson's spec; each module's old per-file nuance survives as a `Priority:` line in the intro, above the section headings. _(2026-09-19)_

- **One database per worktree is the convention; `DATABASE_URL` in `server/.env` is the only thing that enforces it, and `.env` is gitignored.** A fresh worktree therefore inherits `devdigest` by default and starts writing to the same `drizzle.__drizzle_migrations` as every other checkout — journals diverge, and `db:migrate` fails with `42701 column ... already exists` against a schema that already has the column. Fix: `CREATE DATABASE devdigest_<branch> OWNER devdigest` in the same container, then point `.env` at it. `POSTGRES_DB` in either `docker-compose.yml` will NOT create it — that variable only applies when the `devdigest_pgdata` volume is first initialised, and it already exists. Nothing else is shared: clones follow `DEVDIGEST_CLONE_DIR=./clones` (relative, resolved against `server/`), secrets sit in `~/.devdigest/secrets.json`, and both test paths use their own throwaway Postgres. Documented in `README.md` under "One database per worktree". _(2026-09-20)_
- **`server/.env` and `server/.env.example` drift silently, and `WEB_PORT` is the expensive one to get wrong.** `app.ts:90` registers CORS with exactly one origin, `http://localhost:${WEB_PORT}` (`config.ts:77`). A local `.env` carrying `WEB_PORT=3005` while the client runs on 3000 (hardcoded in `client/package.json`, and what `dev.sh:109` starts) leaves the API up, `/health` green and SSR pages at 200 — while every browser fetch from the web app is dropped for a missing `access-control-allow-origin`. Nothing logs it server-side. Check with `curl -sD- -o/dev/null -H 'Origin: http://localhost:3000' localhost:3001/repos` before assuming the stack is healthy. _(2026-09-20)_

- **A linked worktree inherits the tracked `.env.example` but never the untracked `.env`, and every downstream failure is silent.** `dev.sh` copies the example when `.env` is missing, so a fresh worktree boots with syntactically valid but *blank* API keys. `LocalSecretsProvider.get()` (`server/src/adapters/secrets/local.ts:40`) then falls through the stored `~/.devdigest/secrets.json` to `process.env` and returns `undefined`; `container.github()` throws `ConfigError: GITHUB_TOKEN is not configured`; and `modules/pulls/routes.ts:38` catches it, logs a `warn`, and serves persisted PRs — so `GET /repos/:id/pulls` returns `200 []` and the UI renders "No pull requests" for a repo that has open PRs on GitHub. Nothing surfaces as an error anywhere. Note the asymmetry that masks it: keys already written to `~/.devdigest/secrets.json` (that store is global, outside every worktree) keep working everywhere, so OpenRouter reviews run fine while GitHub silently does not. Fix: `./scripts/sync-env.sh`, now called from `dev.sh` — it fills only keys that are absent or empty locally, so the per-worktree `DATABASE_URL` and ports survive. Diagnose with `curl -s localhost:3001/settings/test-connection -d '{"provider":"github"}' -H 'content-type: application/json'`, which reports the real reason. _(2026-09-20)_
- **`tsx watch` does not reload `server/.env`.** `dotenv/config` runs once per process (`server/src/platform/config.ts:1`), so editing `.env` under a running dev server changes nothing — and the stale value is invisible, since the API stays green. `touch server/src/server.ts` is enough to make the watcher respawn the child, which re-reads the file (~2s). Provider clients are cached on the container as well (`_github`, `llmCache`); the only in-process way to drop them is `invalidateSecretCaches()`, which currently has exactly one caller — `POST /settings/test-connection` when it is given a key. _(2026-09-20)_

- **Agent rules live in `AGENTS.md`; each directory's `CLAUDE.md` is a one-line `@AGENTS.md` stub, and a new nested `AGENTS.md` needs its own stub** — Claude Code 2.1.283 loaded root+nested `AGENTS.md` without stubs in only 5 of 6 `claude -p` runs in a scratch repo (5 of 5 with stubs), so a stub-less `AGENTS.md` may silently not reach Claude Code sessions; rules written into a stub reach Claude Code only, not Cursor/Antigravity. See `docs/adr/0004-agents-md-as-instructions-source.md:14`. _(2026-09-28)_

## Tool & Library Notes

- **`pnpm <script>` fails in this environment before the script even starts.** pnpm 11.5.3 via corepack runs a preflight `pnpm install` that exits 1 on `[ERR_PNPM_IGNORED_BUILDS]` (esbuild, sharp) — so `pnpm typecheck` / `pnpm test` look broken while the code is fine. `node_modules` is complete; call the binary directly (`./node_modules/.bin/tsc`, `./node_modules/.bin/vitest`) or run `pnpm approve-builds` once. Affects every package. _(2026-09-19)_

## Recurring Errors & Fixes

- **`./scripts/dev.sh` cannot complete on this machine: it dies at `applying migrations`, hitting both known blockers in sequence.** First `pnpm db:migrate` exits 1 on `[ERR_PNPM_IGNORED_BUILDS]` (the preflight-install issue above) — and `--config.strict-dep-builds=false` / `npm_config_*` env vars do NOT help, because the preflight `pnpm install` is spawned as a separate process that ignores the outer invocation's flags; only an `.npmrc`/`package.json` config or `pnpm approve-builds` would. Second, even bypassing pnpm, `tsx src/db/migrate.ts` fails with `42701 column "cost_usd" of relation "agent_runs" already exists`. Working bring-up that needs no file changes: `docker start devdigest-postgres`, then `server/node_modules/.bin/tsx src/db/seed.ts` (seed alone — skip migrate, the shared DB is already ahead), then `server/node_modules/.bin/tsx watch src/server.ts` and `client/node_modules/.bin/next dev -p 3000`. Verified: `/health`, `/repos`, `/workspace`, `/agents`, `/settings` all 200. _(2026-09-20)_
- **The shared DB has drifted further since 2026-09-19: `agent_runs.cost_source` now exists too** (the earlier Open Questions entry recorded it as missing), along with the `agent_runs_pr_ran_at_idx` index — i.e. everything migration `0010` (`server/src/db/migrations/0010_mysterious_madame_hydra.sql`) wants to add is already present, which is exactly why it fails. The drift is one-directional and keeps growing as other worktrees migrate the same container. _(2026-09-20)_

- **`[ERR_PNPM_IGNORED_BUILDS]` is cleared only by filling the `allowBuilds:` placeholders pnpm auto-writes into each package's untracked `pnpm-workspace.yaml`.** pnpm 11.5.3 generates `server/pnpm-workspace.yaml`, `client/pnpm-workspace.yaml` and `reviewer-core/pnpm-workspace.yaml` carrying an `allowBuilds:` map whose values are the literal string `set this to true or false` (visible via `pnpm config list`). Until every key is an explicit `true`/`false`, the `runDepsStatusCheck` preflight spawns `pnpm install`, that exits 1, and every `pnpm <script>` dies before it starts — `typecheck`, `test`, `db:migrate`, and therefore `./scripts/dev.sh` and `./scripts/e2e.sh` too. Setting all keys to `false` is correct here: the stack demonstrably runs with none of those builds executed (dev server, tsx, vitest, drizzle-kit), and `cpu-features` is a native compile that commonly fails. Caveat: `sharp: false` in `client/pnpm-workspace.yaml` may cost the Next image optimizer its fast path in a production build. The files are untracked, so every fresh clone and every new worktree hits this once. _(2026-09-20)_

- **A hermetic `./scripts/e2e.sh` run silently breaks the dev app on :3000 — it shares `client/.next` with the running dev server.** `scripts/e2e.sh:148` starts the isolated web tier with `pnpm exec next dev -p "$WEB_PORT"` from the same `client/` directory while exporting `NEXT_PUBLIC_API_BASE=http://localhost:3101`, so that base is baked into the shared build output. After teardown :3101 is dead and the dev app renders "Cannot reach the DevDigest engine" while `curl localhost:3001/health` still returns 200 — the API is fine, the bundle is not. Confirm with `grep -rl localhost:3101 client/.next/static`. Recovery: kill the `next dev -p 3000` process, `rm -rf client/.next`, restart it. The script's own header claims it is safe to run alongside a live dev stack; that holds for the database and not for the client bundle. A real fix needs a separate `distDir` for the hermetic run. _(2026-09-20)_

- **`server` typecheck in a fresh worktree fails with `../reviewer-core/src/llm/structured.ts: Cannot find module 'zod'` / `'openai'`, plus follow-on `Type 'unknown' is not assignable to type 'T'` in `src/adapters/llm/*.ts`** — `server/tsconfig.json` resolves `reviewer-core` to its TS source, and that source resolves imports from `reviewer-core/node_modules`, which a new worktree does not have. Fix: `cd reviewer-core && pnpm install` too; the `unknown`→`T` errors are downstream of the missing `zod` types, not real. Seen via `npx tsc --noEmit -p server/tsconfig.json`. _(2026-09-28)_

- **A `pnpm <script>` spawned with `CI` set can wipe the package's `node_modules`; afterwards every script dies with `Cannot find module '…/node_modules/typescript/bin/tsc'`.** pnpm 11.5.3's pre-run deps check spawns `pnpm install`; with `CI` in the environment it purges and recreates the modules dir without asking (without `CI` it stops at `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`), then exits on `ERR_PNPM_IGNORED_BUILDS` and leaves a half-empty `node_modules/.ignored`. Seen on server, client and reviewer-core after scripted `pnpm typecheck` runs. Fix: reinstall (`pnpm install --frozen-lockfile` in client/server, `npm ci` in reviewer-core). Prevention for anything that runs pnpm scripts from code: set `pnpm_config_verify_deps_before_run=false`, which does disable the check; the `npm_config_` spelling does not (`.claude/skills/pr-self-review/scripts/self-review.mjs:187`). _(2026-09-28)_

- **`pnpm install` in `reviewer-core/` deletes its `node_modules` and then fails with `ERR_PNPM_NO_LOCKFILE`.** reviewer-core (and e2e) are npm packages: the lockfile is `reviewer-core/package-lock.json` and CI runs `npm ci` (`.github/workflows/reviewer-core.yml:45`). pnpm prints `Recreating …/reviewer-core/node_modules` before it discovers there is no `pnpm-lock.yaml`, so the attempt leaves the package with no dependencies at all, which breaks `server` typecheck too. Use `cd reviewer-core && npm ci`. _(2026-09-28)_
